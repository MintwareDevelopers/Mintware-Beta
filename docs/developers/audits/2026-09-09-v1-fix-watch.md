## 22:52 UTC check — exact-PM selector breaks env-bootstrap exits

The pending historical-instance routing fix introduces a concrete fallback regression. In `lib/gateway/routeInstance.ts`, the new `wantPm && raw` branch searches registry rows and returns 404 before reaching the empty-registry env fallback. The same configured env pool/PM resolves successfully without the PM selector but fails with its correct PM supplied.

This is now reachable by normal bootstrap flows: `positions` returns positionManager even for an env-fallback instance; Portfolio links append `?pm=`; metadata/position pass that selector through. Those links now 404. Withdrawal recording unconditionally derives positionManager from receipt.to, so a legitimate env-PM withdrawal also fails recording when the registry is empty. The on-chain withdrawal itself is not blocked by this backend record failure. This is conditional on the deliberately supported empty-registry bootstrap configuration, not a claim about current production state.

Executable evidence: `tests/audit-v1-watch-env-20260909.test.ts` runs the real resolver with an empty fake registry and confirms success without selector versus pool_not_live with the exact correct PM. It deliberately asserts defective behavior. Fix by validating an explicit selector against the env PM only after positively establishing the registry is empty; preserve registry fail-closed and unknown-PM rejection. Add control coverage for both empty-registry exact-match and mismatched-PM cases.

The historical selector is now threaded through metadata, position reads and receipt-derived withdrawal resolution; full closure is still under review. Portfolio React keys remain pool-only at this observation, and cost basis is explicitly still shared between generations.
